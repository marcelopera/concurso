# Migração do histórico após o merge

Autorização do proprietário: realizar a reescrita somente depois da aprovação e do merge deste PR. Destino escolhido para o backup: diretório irmão `concurso_codex`. Esta é uma cópia local; a exigência original de cópia fora da máquina foi substituída explicitamente pelo proprietário. Nenhum comando deste roteiro foi executado como reescrita pelo PR.

1. Confirmar que o PR foi aprovado pelo proprietário e está `MERGED`, conferir seu commit final na `main` remota e interromper gravações concorrentes. Salvar a configuração atual de proteção e a lista de branches e tags.
2. Há uma execução preliminar verificada em [docs/runs/issue-23-backup-evidence.md](runs/issue-23-backup-evidence.md): o espelho e o snapshot representam apenas o que foi encontrado antes do merge. Antes de reescrever, criar em `concurso_codex/backups/<identificador>/` um novo `git clone --mirror` do remoto, executar `git fsck --full` e salvar `git show-ref`. Localizar e copiar o acervo original para um snapshot separado, preservando lotes, correções, metadados, PDFs e bancos de progresso existentes; verificar o manifesto da origem e executar ensaio de restauração. O destino deve ficar fora da origem ou a cópia deve excluir explicitamente a si própria para evitar recursão. Não usar apenas um clone do código como backup dos dados ignorados. Se a fonte original continuar ausente, interromper antes da reescrita.
3. Gerar os manifestos SHA-256 fora das pastas inventariadas com `tools/dataset_manifest.py create` e validá-los com `verify` contra as cópias. Inventariar a fonte antes da cópia e verificar o destino contra esse manifesto. Registrar proveniência conhecida e campos desconhecidos. Não remover o arquivo privado original após a cópia.
4. Criar outro clone espelho para a reescrita; nunca executar `filter-repo` no único backup. Gerar a lista explícita de caminhos com `python tools/history_cleanup_plan.py <clone-de-trabalho> <plano.json>`. Inspecionar `remove_paths` e as refs antes de usar a lista com `git filter-repo --invert-paths --paths-from-file <caminhos.txt>`. A lista contém apenas nomes de caminhos, um por linha. Não fornecer o JSON diretamente ao filter-repo.
5. Aplicar um mailmap das identidades pessoais do proprietário para `65731000+marcelopera@users.noreply.github.com`, preservando identidades de outros contribuidores e bots. Comparar árvores do código atual antes/depois, rodar testes e confirmar ausência de dados proibidos em todas as refs. Examinar objetos grandes remanescentes antes de aprovar o conjunto final de refs.
6. Temporariamente ajustar a proteção apenas para a migração autorizada. Enviar as refs revisadas por branch/tag, verificando os SHAs remotos anteriores; não usar `push --mirror` indiscriminadamente, que também pode excluir refs novas. Restaurar imediatamente a proteção da `main` e seus oito checks, inclusive em caso de falha.
7. Repetir `git fsck`, medir `git count-objects -vH` em um clone completo novo e procurar os caminhos removidos em todo o histórico. Não medir apenas a árvore atual nem um clone raso. Documentar a redução real; dezenas de MB é o objetivo, não um número presumido.
8. Coordenar substituição dos clones antigos para não reintroduzir objetos. Conferir refs de PRs e caches do GitHub separadamente: a remoção das branches não comprova o desaparecimento dessas cópias. Registrar a primeira release de código `v0.1.0` apenas no commit já limpo, sem assets privados, e atualizar a issue com evidências.

A integridade dos dados e o êxito da reescrita devem ser registrados separadamente. Um hash confirma que a cópia é igual à fonte; não confirma autoria, licença ou proveniência sem registros reais. A release e a limpeza continuam pendentes até essa etapa posterior.
